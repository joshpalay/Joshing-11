## 2. Top findings

1. **Claim 2 is REFUTED as literally stated.** `src/server/db/queries/activity.ts:237-243` reads from `friendships` in production (not a script, not a test) — to hydrate legacy `referenceType: 'friendship'` activity rows. It's read-only and its own comment calls it a "legacy" path, but it is live, load-bearing production code, not merely "retained for rollback." Two non-test *scripts* (`scripts/playtest/lib/cleanup.ts` — writes/deletes; `scripts/playtest/scenarios/accept-invitation.ts` — reads) also touch it.
2. **Claim 6 is REFUTED.** `src/instrumentation.ts:1690-1712` contains raw `INSERT INTO "Follow" ...` SQL — an idempotent boot-time backfill guard (migration 0058's defensive re-run path) that writes to `follows` entirely outside `friendships.ts`. It's `ON CONFLICT DO NOTHING` and clearly a migration-repair guard, not application logic, but it is a real write path outside the module named as sole owner.
3. **A dead/misleading blocking check.** `RelationshipResult.isBlocked` (`src/server/db/queries/friend-requests.ts:26-59`) is hardcoded `false` on every single code path, with its own comment admitting "Explicit blocking is not modelled under the follow model... this is always false now." But `src/server/db/queries/friend-search.ts`'s comment still claims the search function "Returns null when... the matched user has soft-removed the viewer (**block detection via getRelationship.isBlocked**)" and the code actually does `if (relationship.isBlocked) return null` — dead code guarded by a comment describing behavior that can never fire. This directly reinforces claims 14/15/17 (no real blocking exists) but is a clean example of comment/code divergence.
4. **Claim 26 (open question) — one more exposure path found:** admin-only fuzzy user search exists (`admin-questions.ts:468` `ilike(users.displayName, ...)`, `points-diagnostic.ts:106/108` `ilike` on displayName/email) — not reachable by ordinary users, so it doesn't contradict claim 22's "no fuzzy search" for the *friend-discovery* surface, but it does mean fuzzy/substring name search isn't literally absent from the codebase, only from the reachable discovery surface. No leaderboard, ceremony, or gameplay-chat surface exposes strangers — `ceremony/room.tsx` and `GameplayChat.tsx` were checked directly; neither renders profile links to non-friends.
5. **Claim 31 is PARTIAL/misleadingly framed.** `ContactMatchBlock` does **not** return null "when discoverableByContacts is false" — it returns null only when `!supportsContactsAPI()` (Chrome-on-Android only). When the API *is* supported but `discoverableByContacts` is false, it renders a visible opt-in card, not null. The causal claim is backwards from the code's actual branch order (`src/components/friends/ContactMatchBlock.tsx:77-81`).

## 4. Answers to the open questions

**Claim 5** — Cannot be determined statically; the schema confirms the *default* is `approval_required`, but the live count of `public` rows requires a database query, which this audit was barred from running.

**Claim 26** — Beyond the seven listed paths, this audit found: (a) admin-only fuzzy name search (not reachable by regular users — noted in claim 22); (b) the `getInviterForUser` fallback comment (`invite-links.ts:148-150`) references a rare case of "an organic mutual follow... without going through a link at all" within an attribution window — this isn't a new *discovery* mechanism, just a case the link-attribution system tolerates. No leaderboard, ceremony-room, or gameplay-chat surface exposes a stranger's identity/profile — `ceremony/room.tsx` and `GameplayChat.tsx` were read directly and neither links to or names non-friend participants.

**Claim 28** — Concretely, what exists: (1) a two-person shared-domain computation (`common-ground.ts`) that only runs between the viewer and one already-specified other user, not a candidate pool; (2) a genuine social-graph mutual-friends *intersection* (`src/server/profile/friend.ts:189-206`, via `getFriends(viewerId)` ∩ `getFriends(profileOwnerId)`), but it's bound to a specific profile page the viewer is already looking at (`/users/[id]`) — it answers "who do we both know," never "who do I not know that I might." No friends-of-friends candidate-enumeration query exists anywhere in the codebase (grepped for `friendOfFriend`, `twoHop`, `secondDegree`, and variants — zero hits outside comments about an unrelated two-hop *feed-forward* attribution mechanism). Building a real "People You May Know" surface needs, at minimum, a new query that starts from the viewer's friend list and enumerates *their* friends excluding the viewer's existing connections/pending requests — that query does not exist today in any form, adjacent or otherwise. The mutual-friends *display* component (`MutualFriendsSection.tsx`) is reusable, but the actual candidate-discovery query is unwritten.

**Claim 31** — Only Chrome on Android reaches a working Contacts-Picker path (`navigator.contacts.select` gate, `ContactMatchBlock.tsx:74`). Every other browser/platform — iOS Safari, all desktop browsers, Chrome on desktop — gets `null` from `supportsContactsAPI()` and the whole component renders nothing, regardless of the `discoverableByContacts` setting.

**Claim 33** — Six distinct user-facing surfaces carry "handle" or "call sign" copy: (1) login/signup handle-claim step (`LoginPanel.tsx`, "Call sign / handle" label + 5 error strings); (2) onboarding name+handle step (`OnboardingFlow.tsx`, "Your call sign" + helper/error text); (3) the privacy policy page's data-collected list (`privacy/page.tsx`); (4) the Friends-page search field (`FindFriendsSearch.tsx`, "@handle or (415) 555-1234"); (5) the privacy settings discoverability description (`PrivacyForm.tsx`, "your @handle or phone number"); (6) the profile-edit handle field placeholder (`InlineHandleField.tsx`). Methodology: grepped `src/app/**/*.tsx` and `src/components/**/*.tsx` for literal "handle"/"call sign" strings, excluding `handleClick`-style identifiers — a keyword scan, not an exhaustive manual UI walk, so treat the count as a lower bound.

- Whether the `7162f03b` invite-link redesign (currently only on `claude/hearted-bank-protection`, not `main`) changes any of claims 9/10/29-31 once merged — this audit covered `main` only, as instructed; a follow-up pass would be needed once/if that branch merges, since it touches `InviteLinksSection.tsx`, `AcceptFriendInvitationButton.tsx`, `AcceptInviteLinkButton.tsx`, and `friends/page.tsx` substantially (658/113/etc. line diffs).
- Whether the raw-SQL `Follow` backfill in `instrumentation.ts` (Top Finding #2) has actually fired in production recently, or is purely dormant defensive code on a fully-migrated DB — that's a runtime/log observation, not something static reading can settle.
- This audit did not exhaustively grep every `.tsx` file in the repo for claim 33 — six surfaces is what a targeted keyword scan turned up; a full manual sweep could turn up more (e.g. transactional SMS/email copy, which wasn't checked).
